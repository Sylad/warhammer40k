Commande unique, sous un Node accepté par Angular 20 (`engines` : `^20.19.0 || ^22.12.0 || >=24.0.0`,
la même plage dès 20.0.0 et jusqu'en 20.3, mesurée par `npm view @angular/core@20.0.0 engines` ;
un Node 20.11 à 20.18 ou 22.0 à 22.11 est refusé par toute la 20) :

```bash
npx ng update @angular/core@20 @angular/cli@20
```

Elle réécrit `package.json` (plages `^20.3.x`, `typescript ~5.9.3`), le `package-lock.json`, et
joue les migrations obligatoires. Sur une application autonome sans rendu serveur, une seule
modifie des fichiers :

- **`@angular/cli` — « Update workspace generation defaults to maintain previous style guide
  behavior »** : ajoute à `angular.json` un bloc `schematics` (`type: component`, `directive`,
  `service` ; `typeSeparator: "."` pour guard, interceptor, module, pipe, resolver). Raison : depuis
  la v20, `ng generate` suit le nouveau guide de style (fichier `foo.ts` et classe `Foo` au lieu de
  `foo.component.ts` / `FooComponent`, séparateur `-` au lieu de `.`). Le bloc garde l'ancienne
  convention pour les fichiers générés ensuite ; il ne renomme rien. À garder si le projet veut des
  noms homogènes.

Migrations sans effet si le code n'utilise pas l'API visée : `DOCUMENT` déplacé de `@angular/common` vers
`@angular/core`, suppression de `InjectFlags`, `TestBed.get` → `TestBed.inject`,
`moduleResolution: "bundler"` (rien à faire s'il est déjà en place), `provideServerRendering` / `BootstrapContext`
(rendu serveur), fichiers karma par défaut.

Migrations **optionnelles** proposées (à lancer séparément, pour garder la montée à périmètre constant) :
`control-flow-migration` (`*ngIf` → `@if`), `router-current-navigation`
(`Router.getCurrentNavigation()` → signal `Router.currentNavigation()`, déprécié en 20.2),
`use-application-builder` (passage au constructeur `@angular/build:application`, sans objet s'il est déjà utilisé).

### Changements cassants de la 20.0.0, confrontés au code

Source : sections « Breaking Changes » de 20.0.0 des CHANGELOG d'`angular/angular` et
d'`angular/angular-cli`, et les étapes `possibleIn: 2000` du guide de mise à jour
(`adev/src/app/features/update/recommendations.ts`, ce que montre update.angular.dev). Pour
chacun : ce qui casse, comment le détecter, la correction.

**Gabarits (compilateur)** — détectés par `ng build` avec `strictTemplates`.

- `in` et `void` dans une expression de gabarit sont désormais les **opérateurs** JavaScript :
  `{{ void }}` ou `{{ in }}` ne lisent plus une propriété du composant. Symptôme : erreur de
  compilation ou valeur `undefined`. Correction : `{{ this.void }}`.
- **Les parenthèses sont respectées** : `{{ (a?.b).c }}` court-circuitait en v19, lève en v20
  `TypeError` si `a` est nul (comportement JavaScript natif). Symptôme : erreur à l'exécution,
  pas forcément à la compilation.
  Détection : `grep -rnE "\?\.[A-Za-z_]+\)[.\[]"` dans les gabarits et les `template:` en ligne.
  Correction : `{{ a?.b?.c }}`.
- Nouveau diagnostic étendu : fonction de suivi non appelée dans `@for (… ; track maFn)`
  (avertissement ; correction `track maFn($index, item)` ou `track item.id`).
- Les liaisons d'hôte (`host: {…}`, `@HostBinding`) peuvent être **vérifiées en type** (option
  `angularCompilerOptions.typeCheckHostBindings`, activée dans les nouvelles applications) ; elle
  vaut `false` par défaut, un projet mis à jour n'est donc pas touché tant qu'il ne l'active pas.

**`@angular/core`**

- TypeScript < 5.8 refusé (`ng update` monte TypeScript ; un `typescript` épinglé ailleurs, par
  exemple dans un monorepo, bloque l'installation).
- `afterRender` renommé `afterEveryRender` (`afterNextRender` inchangé).
- `TestBed.flushEffects()` supprimé → `TestBed.tick()`.
- `TestBed.get` et `InjectFlags` supprimés (migrations automatiques) ; `Injector.get` n'a plus de
  surcharge `any` : le jeton doit être un `ProviderToken<T>` (ou une chaîne, dépréciée).
  Symptôme : erreur de type à la compilation d'un `injector.get(x as any)`.
- `provideExperimentalZonelessChangeDetection` → `provideZonelessChangeDetection` ;
  `provideExperimentalCheckNoChangesForDebug` → `provideCheckNoChangesConfig` (option
  `useNgZoneOnStable` supprimée).
- `PendingTasks.run` ne renvoie plus le résultat de la fonction asynchrone (utiliser
  `PendingTasks.add` et gérer soi-même la promesse).
- **Erreurs non rattrapées dans un écouteur d'événement** (`(click)="…"`) : remontées en plus au
  mécanisme interne d'Angular ; **en test, elles sont relancées** au lieu d'être seulement
  journalisées. Symptôme : un test qui passait « malgré » une erreur console échoue. Correction :
  corriger l'erreur, l'attendre explicitement dans le test, ou en dernier recours
  `TestBed.configureTestingModule({ rethrowApplicationErrors: false })`.
- `ApplicationRef.tick()` ne rattrape plus les erreurs : elles sortent de l'appel au lieu d'aller à
  l'`ErrorHandler`.
- Les animations sont toujours vidées à chaque détection de changements ou `ApplicationRef.tick()` :
  un test qui vérifiait qu'un élément « devait être retiré mais ne l'était pas encore » change de
  résultat.
- **Attributs `ng-reflect-*` plus produits** (même en mode dev). Symptôme : sélecteurs de test ou
  scripts e2e qui ciblent `[ng-reflect-…]` ne trouvent plus rien. Correction : cibler un attribut
  explicite (`data-testid`, `aria-*`) ; transitoirement `provideNgReflectAttributes()`.

**`@angular/common`**

- `AsyncPipe` rapporte lui-même à l'`ErrorHandler` les erreurs d'une souscription ou d'une
  promesse ; même résultat dans une application avec zone.js, mais un test qui espionnait la
  remontée par zone.js peut devoir être revu.
- `DatePipe` / `formatDate` : un motif avec `Y` (année de semaine ISO) sans `w` lève
  `NG02300` « Suspicious use of week-based year "Y" » **en mode développement seulement**
  (`ngDevMode` ; le motif `'YYYY'` seul n'émet qu'un `console.error`) — c'est presque toujours `y`
  qui était voulu (`'dd/MM/YYYY'` → `'dd/MM/yyyy'`, qui donnait une année fausse du 29 décembre
  au 3 janvier certaines années). Symptôme : page en erreur sous `ng serve` et dans les tests,
  rien en production ni au build. Détection : chercher `Y` dans les motifs passés à `| date` et `formatDate`.

**`@angular/router`**

- `RedirectFn` (`redirectTo` en fonction) peut renvoyer un `Observable` ou une `Promise` : le code
  qui appelle lui-même une telle fonction doit traiter ces types.
- Les tableaux de gardes d'une `Route` (`canActivate`, `canMatch`…) n'acceptent plus `any` :
  fonction de garde, `ProviderToken<T>` ou chaîne (dépréciée). Symptôme : erreur de type.
- `redirectTo` combiné à `canMatch` sur la même route est une erreur.
- Paramètres tableaux de l'API du routeur passés en `readonly T[]` (sans effet pour l'appelant).

**Outillage (`@angular/cli`, `@angular/build`)**

- Node hors `^20.19 || ^22.12 || >=24` refusé (Angular 20.3) : vérifier l'image Docker du build et la CI avant
  `ng update`.
- `@angular/build` 20 embarque vite 7 et sass 1.90 : les avertissements de dépréciation Sass
  (`mixed-decls`) restent des avertissements, sans changement de rendu.

**Dépréciations de la 20 (encore valides, à traiter avant la 21 ou la 22)** :
`*ngIf` / `*ngFor` / `*ngSwitch` (migration `control-flow-migration`), tout le paquet
`@angular/platform-browser-dynamic` (y compris `/testing` : `platformBrowserDynamicTesting` →
`platformBrowserTesting` de `@angular/platform-browser/testing`), le support HammerJS,
`Router.getCurrentNavigation()`, et **tout le paquet `@angular/animations`** (déprécié en 20.2,
retrait annoncé en v23 ; `npm ci` affiche « @angular/animations@20.3.x: deprecated, use
animate.enter / animate.leave ») : `provideAnimations()`, `provideAnimationsAsync()`,
`BrowserAnimationsModule`, `NoopAnimationsModule` et les déclencheurs `trigger()` / `@monTrigger`
des composants. Remplacement : les liaisons natives `animate.enter` / `animate.leave` (classes CSS,
v20.2+) ou de simples transitions CSS. C'est la dépréciation la plus coûteuse pour une
application qui anime ses composants avec `trigger()` : la recenser dès cette montée
(`grep -rnE "trigger\(|provideAnimations|BrowserAnimationsModule"`), la migrer avant la 23.
