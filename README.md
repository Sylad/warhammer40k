## Pourquoi

Dev Java/web depuis 2005, j'utilise ce projet pour explorer **Claude Code** sur un stack frontend que je ne pratique pas au quotidien : **Angular 19 + NestJS**.

Le sujet (W40K) est volontairement riche en lore + visuel pour pousser sur les enjeux UX : navigation hiérarchique, cards image-first, fil narratif central, intégration de sources externes (Wikipedia/Fandom, Reddit, 40k.gallery).

Mon rôle : direction artistique + cadrage du besoin.
Le rôle de Claude : poser le code, expliquer chaque choix, itérer.

En amont du code, [ChatGPT](https://chat.openai.com) a aidé à générer les premières maquettes UX et schémas de pages — point de départ visuel pour l'identité gothique noir/or.

```bash
git clone <ce-repo> warhammer40k
cd warhammer40k

cp backend/.env.example backend/.env
# Édite ANTHROPIC_API_KEY

(cd backend && npm install) && (cd frontend && npm install)
npm run dev:backend    # API NestJS sur http://localhost:3001
npm run dev:frontend   # dans un autre terminal
```

## Étape spec (cadence)

**Onglets de la fiche unité (L121)** — la barre Aperçu · Équipement · Histoire & Lore · Variantes est une `<nav aria-label="Sections de la fiche">` ; le bouton actif porte `aria-current="true"` (absent sur les autres), pour que l’état soit annoncé et pas seulement coloré (WCAG 4.1.2). Gardé par `features/unit-detail/unit-detail.component.spec.ts`.

**Onglet Variantes (L126)** — l’onglet n’est proposé que si l’unité a des `variants` (1 fiche sur 133 : l’Intercessor). Une carte sans `image` prend le visuel de l’unité (ou le dégradé de la faction), plus aucune requête wiki « arme » ; les cartes n’ont ni curseur main ni survol, aucune action n’y étant attachée. Gardé par `unit-detail.component.spec.ts`.

**Suite déterministe sous charge (L113)** — `frontend/vitest.config.ts` borne le parallélisme (`maxWorkers: 8`, au lieu d'un worker par cœur : une vingtaine de specs pilotent Chromium et plusieurs parcourent `dist/`) et donne 30 s par test (comme `vitest.e2e.config.ts`) au lieu des 5 s par défaut : le scan de fuite de `dist/` de `plan-data.test.mjs` (~1 s au repos) expirait au hasard de la charge. `scripts/vitest-charge.test.mjs` garde ces réglages. Cas « cible à 92 px sous la barre » (`ancres.e2e.spec.ts`, échec d'assertion, pas de délai) : cause NON reproduite malgré des retards de 1,5 s sur les requêtes réelles de la fiche primarque (`/api/lore/primarchs/:id`, `/api/wiki-image`, en plus de `units` et `subfactions`, utilisées par les fiches faction) et de 2,5 s sur les polices (cas primarque 390 px rejoué seul, vert) ; l'hypothèse « fenêtre de stabilité trop courte » est démentie, la mesure reste donc gardée par trois dispositifs : `trackSettled` (la page ne reçoit son clic qu'une fois réglée — aucune requête en vol, polices chargées, deux images de suite ; plus de `networkidle`, déconseillé par Playwright), une fenêtre de stabilité qui repart tant qu'une police charge, et un échec explicite « position instable » au plafond de 20 s. Même famille, hors de ce lot : `videos-ouvrir-l47` peut lire l'adresse d'un nouvel onglet encore à `about:blank` (test scellé de L47, laissé tel quel ; aucun lot de ce plan ne le suit : le rescellement d'un lot livré relève de cadence L212, et l'échec CI reste possible d'ici là). **L166** : cet échec est survenu (clic du milieu, R9, `waitForEvent` 8 s, run 39809792648), comme ceux de L49 R3 (`boundingBox` 4 s, 18-10) : toujours un délai, jamais une assertion fausse, sur des fichiers différents, quand les trois fichiers de `npm run test:e2e` (un Chromium chacun) tournaient en parallèle sur le runner ; la durée du fichier de L47 ne montre aucune charge (32,9 à 36,8 s dans cinq runs verts, 40,0 et 42,6 s dans les deux rouges : l'écart d'environ 6 s est compatible avec le délai de 8 s de `waitForEvent` mais ne le prouve pas ; le « 27 s » d'une première version venait d'un run lui-même rouge). Cause non prouvée sur la CI (aucune reproduction locale en 25 essais sous charge) : l'étape e2e de « Contrôles frontend » conserve désormais la durée de chaque cas (rapport junit, artefact `e2e-junit`, même en échec) et la charge du runner (`nproc`, `uptime`), et `workflow_dispatch` permet de rejouer une série de runs ; le journal horodaté de chaque appel Playwright (`DEBUG=pw:api`, sans toucher aux specs scellées : clic fait ou non, onglet ouvert ou non, `waitForEvent` abouti ou expiré) est joint au même artefact (`e2e-pwapi.log`), qui sépare les trois causes possibles d'un rouge ; `vitest.e2e.config.ts` passe à `fileParallelism: false` (un navigateur à la fois), gardé par `scripts/vitest-charge.test.mjs` (R1). La charge est échantillonnée toutes les 2 s pendant les e2e (`e2e-charge.log`, même artefact), l'`uptime` d'avant le lancement ne reflétant que le build. Une reproduction locale existe pour la même famille, hors lot : `section-anchor-href-l160.e2e.spec.ts` (Control+clic d'une faction) a échoué une fois dans `npx vitest run` (suite complète, 8 workers), `waitForEvent('page')` expiré à 20 s, et passe 3 fois sur 3 seul ; son délai avait déjà été porté de 8 à 20 s sans effet. Sous charge l'onglet peut donc ne jamais s'ouvrir (clic fait, pas de page) plutôt qu'arriver en retard : **allonger le délai d'attente n'est pas le remède**, lire `e2e-pwapi.log` avant. Si un rouge revient malgré cela, la cause est ailleurs que la concurrence entre fichiers. Les specs qui lisent `dist/` ne le reconstruisent jamais : `npm run build` avant `npm test`, pas pendant.

Un lot à écran (`screen:`) passe par l'étape spec de cadence (`orchestrate.spec` dans `cadence.yaml`) : fiche et maquette sous `docs/specs/<écran>/`, revue de maquette, puis tests d'acceptation rouges. Ces tests sont des `*.acceptation.spec.ts` listés dans `docs/specs/<écran>/acceptation-<lot>.json` ; tant que ce fichier dit `"vert": false`, la suite (`npm test`) et la CI les excluent (`frontend/scripts/acceptation-runner.mjs`, repris d'ol-companion). La commande dédiée `orchestrate.accept` ne lance qu'eux : `cd frontend && CADENCE_ACCEPTATION=../docs/specs/<écran>/acceptation-<lot>.json npx vitest run -c vitest.acceptation.config.ts`. Le cycle pose `"vert": true` quand ils passent, et ils rejoignent alors la suite. Exception : une acceptation qui pilote un navigateur (import de `playwright-core`) reste hors de `npm test` même verte — elle exige `dist` et Chromium — et tourne avec les e2e : `cd frontend && npm run build && npm run test:e2e` (`vitest.e2e.config.ts`, 30 s par cas ; étape dédiée de « Contrôles frontend » après le build).
